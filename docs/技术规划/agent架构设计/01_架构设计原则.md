## 一、核心设计原则

### 1.1 高内聚、低耦合（首要原则）

**定义**:
- **高内聚**: 模块内部元素紧密相关，共同完成单一职责
- **低耦合**: 模块之间依赖最小化，通过明确接口交互

**实施标准**:

| 层级 | 内聚要求 | 耦合要求 | 验证标准 |
|------|---------|---------|---------|
| **工具层** | 单一原子能力 | 无业务逻辑依赖 | 一个工具只做一件事 |
| **核心层** | 编排能力单一 | 通过接口调用工具 | 不包含业务逻辑 |
| **知识层** | 知识领域清晰 | 不依赖具体实现 | 配置可替换 |
| **场景层** | 无代码层 | 纯配置驱动 | 新增场景零代码 |

**设计约束**:

```markdown
❌ 禁止：
- 工具层包含业务判断逻辑
- 核心层硬编码场景处理流程
- 场景层编写Java代码

✅ 必须：
- 工具层：原子操作、无状态、可复用
- 核心层：通用编排、接口驱动、配置加载
- 知识层：配置化、可插拔、独立维护
- 场景层：YAML配置、声明式、可热更新
```

**验证方法**:
- [ ] 工具层代码审查：检查是否有业务逻辑
- [ ] 依赖关系图分析：检查耦合度
- [ ] 新增场景测试：验证是否只需配置

---

### 1.2 可扩展性原则

**定义**: 新增功能或场景时，最小化代码修改量

**量化标准**:

| 场景 | 允许修改范围 | 工作量上限 |
|------|------------|-----------|
| **新增诊断场景** | 仅配置文件 | 30分钟 |
| **新增查询工具** | 工具类+注册 | 2小时 |
| **修改诊断标准** | 仅YAML文件 | 10分钟 |
| **新增异常类型** | 配置+Handler | 1小时 |
| **优化推理逻辑** | Prompt模板 | 20分钟 |

**设计约束**:

```markdown
✅ 扩展点设计要求：
1. 工具注册机制：新工具自动发现
2. 场景配置机制：新增场景无需重启
3. 知识库插拔机制：独立维护更新
4. 异常处理配置化：策略可调整
5. 输出模板配置化：格式可定制

❌ 禁止硬编码：
- 场景处理流程
- 业务判断逻辑
- 异常处理策略
- 输出格式模板
```

**验证方法**:
- [ ] 添加新场景测试：记录实际工作量
- [ ] 代码修改量统计：检查是否超出标准
- [ ] 回归测试：验证扩展不影响现有功能

### 1.4 可测试性原则

```markdown
✅ 必须满足：
1. 每个工具可独立测试（无外部依赖）
2. 每个异常类型有测试用例
3. 配置加载有验证机制

- 工具依赖外部服务无法Mock
```

## 二、架构决策记录（ADR）

### ADR-001: 分层架构选择

**决策**: 采用4层架构（工具层、核心层、知识层、场景层）

**理由**:
- ✅ 高内聚低耦合：每层职责单一，接口清晰
- ✅ 可扩展：新增场景只需配置
- ✅ 可维护：问题定位快速
- ✅ 可测试：每层独立测试

**替代方案**:
- ❌ 单体Service：耦合度高，难扩展
- ❌ 微服务：过度复杂，管理成本高

**影响**:
- 需要设计清晰的接口规范
- 需要完善配置管理机制
- 需要文档化每层职责

**状态**: ✅ 已采纳

---

### ADR-002: 工具层无状态设计

**决策**: 工具层所有组件无状态，纯函数式

**理由**:
- ✅ 高可复用：一个工具可被任意场景调用
- ✅ 易测试：Mock简单，测试独立
- ✅ 易维护：无副作用，问题定位快
- ✅ 易扩展：新工具无需考虑场景依赖

**替代方案**:
- ❌ 有状态工具：需要管理状态，耦合场景
- ❌ 业务逻辑嵌入：违反单一职责

**影响**:
- 业务逻辑必须在知识层或核心层
- 工具只提供原子能力
- 需要编排机制组合工具

**状态**: ✅ 已采纳

---

### ADR-003: 场景层纯配置化

**决策**: 场景层零代码，纯YAML配置

**理由**:
- ✅ 最小化代码修改：新增场景零代码
- ✅ 易维护：配置清晰，易于理解
- ✅ 易更新：配置可热更新，无需重启
- ✅ 易回滚：配置版本化管理

**替代方案**:
- ❌ 场景Java类：每次新增需写代码
- ❌ 硬编码流程：难扩展难维护

**影响**:
- 需要完善的配置加载机制
- 需要配置验证机制
- 需要配置文档化

**状态**: ✅ 已采纳

---

### ADR-004: 异常处理分级策略

**决策**: 异常分级处理（快速失败/优雅降级/透明部分）

**理由**:
- ✅ 用户体验好：明确提示，引导解决
- ✅ 系统鲁棒性：降级策略保证可用
- ✅ 可观测性：异常类型清晰记录
- ✅ 可维护性：每种异常有处理指南

**替代方案**:
- ❌ 统一错误提示：用户无助，体验差
- ❌ 隐瞒异常：误导用户，不可信

**影响**:
- 需要详细异常分类体系
- 需要分级处理策略配置
- 需要异常监控告警机制

**状态**: ✅ 已采纳

---

### ADR-005: 知识层配置驱动

**决策**: 业务规则、诊断标准、Prompt模板全部YAML配置

**理由**:
- ✅ 易维护：业务人员可修改配置
- ✅ 易更新：无需开发介入
- ✅ 易测试：配置验证机制
- ✅ 易审计：配置变更可追踪

**替代方案**:
- ❌ 硬编码逻辑：每次修改需代码
- ❌ 数据库存储：查询慢，难版本化

**影响**:
- 需要配置文件版本化管理
- 需要配置验证和加载机制
- 需要配置热更新机制

**状态**: ✅ 已采纳

## 三、质量标准

### 3.1 代码质量标准

```markdown
✅ 必须满足：
1. 单个文件 ≤ 300行
2. 单个方法 ≤ 50行
3. 单个参数 ≤ 5个
4. 嵌套深度 ≤ 3层
5. 代码注释覆盖率 ≥ 100%（关键逻辑）
6. 命名规范统一
7. 无魔法数字（使用常量）
8. 无硬编码业务逻辑
```

**质量检查清单**:

```bash
# 代码质量检查脚本
- 文件行数检查：find . -name "*.java" -exec wc -l {} \;
- 方法行数检查：grep -r "public|private" | wc -l
- 注释覆盖率：使用SonarQube或Checkstyle
- 命名规范：使用Java Naming Conventions
- 硬编码检测：grep -r "if.*==.*\"" | grep -v "test"
```

---

### 3.2 配置质量标准

```markdown
✅ 必须满足：
1. 配置文件有完整注释
2. 配置项有类型说明
3. 配置项有默认值
4. 配置项有验证规则
5. 配置文件有版本号
6. 配置文件有变更记录
7. 配置文件有示例
```

**配置验证机制**:

```java
/**
 * 配置验证器
 */
@Component
public class ConfigValidator {
    
    /**
     * 验证场景配置
     */
    public ValidationResult validateScenarioConfig(ScenarioConfig config) {
        
        ValidationResult result = new ValidationResult();
        
        // 1. 必填项检查
        if (config.getScenarioId() == null) {
            result.addError("scenario_id is required");
        }
        
        // 2. 类型检查
        if (!config.getDataTools().stream().allMatch(this::isToolExists)) {
            result.addError("data_tools contains invalid tool name");
        }
        
        // 3. 逻辑检查
        if (config.getDataTools().isEmpty() && config.getAnalysisTools().isEmpty()) {
            result.addError("scenario must have at least one tool");
        }
        
        return result;
    }
}
```

### 3.5 安全质量标准

```markdown
✅ 必须满足：
1. 所有API调用需权限验证
2. 用户数据隔离（按userId过滤）
3. 敏感数据脱敏（成本、供应商价格）
4. 输入参数验证（防止注入）
5. 配置文件加密存储（如有敏感信息）
6. 日志脱敏（不记录敏感数据）
7. 异常信息不泄露内部细节
```

**安全检查清单**:

```java
/**
 * 安全验证拦截器
 */
@Component
public class SecurityInterceptor {
    
    /**
     * 权限验证
     */
    public boolean checkPermission(Long userId, String scenario) {
        
        // 1. 检查用户角色
        UserRole role = userService.getUserRole(userId);
        
        // 2. 检查场景权限
        ScenarioPermission permission = permissionService.getPermission(role, scenario);
        
        // 3. 验证权限
        if (!permission.isAllowed()) {
            throw new SecurityException("No permission for scenario: " + scenario);
        }
        
        return true;
    }
    
    /**
     * 数据脱敏
     */
    public Object sanitizeData(Object data, UserRole role) {
        
        // 根据角色脱敏敏感字段
        if (role != UserRole.MANAGER) {
            // 非管理员，脱敏成本、供应商价格等
            return DataSanitizer.sanitize(data, role.getSensitiveFields());
        }
        
        return data;
    }
}
```

## 四、架构约束清单

### 4.1 禁止事项清单（MUST NOT）

```markdown
❌ 工具层禁止：
- 包含业务判断逻辑（if-else业务分支）
- 调用其他工具（工具不能嵌套）
- 依赖特定场景（工具必须通用）
- 管理状态（工具必须无状态）
- 硬编码配置（配置必须外部化）

❌ 核心层禁止：
- 硬编码场景处理流程
- 包含业务规则判断
- 直接操作数据库
- 管理状态（必须无状态）
- 知道具体工具实现细节

❌ 知识层禁止：
- 依赖Java代码实现
- 硬编码在代码中
- 无法独立更新
- 无法版本化管理

❌ 场景层禁止：
- 编写Java代码
- 硬编码业务逻辑
- 依赖特定实现
- 无法动态更新
```

---

### 4.2 必须事项清单（MUST）

```markdown
✅ 工具层必须：
- 单一原子能力
- 无状态设计
- 可独立测试
```
