# 意图识别模块设计

> **文档版本**: v1.0
> **创建日期**: 2026-07-18
> **设计目标**: 将用户自然语言输入精确映射到已实现的评测场景，保证识别准确率 ≥ 95%（简单级）
> **参考依据**: 架构设计原则 v1.0 + 仓库管理员评测集 36题 + 评测标准与评分规范

---

## 一、设计思路

### 核心问题

评测集 36 题覆盖 4 种难度，输入形态差异巨大：

| 难度 | 输入示例 | 特征 | 核心挑战 |
|------|---------|------|---------|
| 简单 | "查询库存列表"、"查看效期预警产品" | 句式和关键词固定 | 精确匹配，零误差 |
| 中等 | "SKU-12345 在各个仓库的库存分布" | 含实体参数(SKU) | 参数提取 + 场景分类 |
| 复杂 | "分析深圳仓本月整体运营效率" | 跨模块、含范围 | 多步骤场景匹配 |
| 模糊 | "仓库的库存情况怎么样"、"东西不够了" | 口语化、指代不明 | 意图澄清 + 选项引导 |

### 设计原则

```
1. 分层兜底 —— 高精确率方案优先，低置信度才上升
2. 置信度区间 —— 不做二元判决，用区间决定行为
3. 评测驱动 —— 配置质量 = 意图识别的上限
4. 简单场景零 LLM —— 纯关键词匹配，零成本
5. 预处理先行 —— 匹配前先重写/扩展/边界检测，减少无效匹配
```

### 匹配策略选择矩阵

| 模糊 #7~#8 | ConversationContext | SemanticMatcher | < 200ms | Rewriter 指代消解 |

## 三、核心概念定义（接口层）

### 3.1 IntentRecognizer — 统一入口

编排整个意图识别链路的入口组件，职责：

1. **先经过 Query Preprocessor 预处理**（见第 8 章）——进行边界检测、重写、扩展
2. 再调用 MultiIntentMatcher 检测是否多意图（"查下库存和异常"）
3. 再调用 KeywordMatcher 做关键词匹配（简单+中等 20 题）
4. 如果 KeywordMatcher 置信度不够，检查 ConversationContext 是否有指代
5. 仍不行则调用 SemanticMatcher 做 LLM 语义匹配
6. 最终根据置信度区间决定行为（直接执行 / 确认后执行 / 返回选项 / 兜底）

匹配链是有序的：**高精确率方案在前，低精确率方案在后**，不会因为 LLM 先入为主而误判。

### 3.2 IntentResult — 识别结果

一次意图识别的输出，包含以下字段：

| 字段 | 说明 |
|------|------|
| sceneId | 场景唯一标识，对应评测用例 ID，如 WM_SIMPLE_001 |
| confidence | 置信度 0.0 ~ 1.0 |
| difficulty | 场景难度 (SIMPLE / MEDIUM / COMPLEX / AMBIGUOUS) |
| params | 提取的参数（如 skuCode, warehouseId, timeRange） |
| candidateScenes | 低置信度时的候选场景列表，供用户选择 |
| needsClarification | 是否需要澄清 |
| needsLLM | 是否需要 LLM 推理 |

根据置信度有四种构造方式：

- **高置信度命中**（≥0.85）：确定一个 sceneId，直接执行
- **中等置信度**（0.50~0.85）：确定一个 sceneId，但需要向用户确认后再执行
- **低置信度**（0.20~0.50）：无确定 sceneId，返回多个候选场景供用户选择
- **完全不匹配**（<0.20）：返回 unknown，走兜底回答

### 3.3 CandidateScene — 候选场景（引导用户选择）

当置信度不足以确定唯一场景时，向用户呈现的选项结构：

| 字段 | 说明 | 示例 |
|------|------|------|
| sceneId | 场景 ID | WM_SIMPLE_001 |
| label | 显示给用户的标签 | 库存汇总 |
| description | 简短描述 | 查看总库存量、SKU 种类、周转率 |
| icon | Emoji | 📦 |
| quickCommand | 快捷指令 | 查看库存汇总 |

用户点击或输入快捷指令后，直接跳转到对应场景。

## 四、KeywordMatcher 详细设计

### 4.1 匹配规则结构

每个场景配置一套关键词规则，包含：

| 配置项 | 说明 | 作用 |
|--------|------|------|
| keywords | 命中关键词（OR 逻辑） | 匹配任一个即触发 |
| requireAll | 必含关键词（AND 逻辑） | 必须全部匹配才触发 |
| excludeKeywords | 排除关键词 | 匹配任一个即跳过该场景 |
| priority | 优先级 | 多场景同时匹配时取优先最高的 |
| paramExtractors | 参数提取规则 | 从输入中提取 SKU、仓库、时间等参数 |
| confidenceFactor | 置信度系数（0~1） | 对模糊输入主动降权，默认 1.0 |

**匹配流程**：

输入 → 归一化（去空格、全角转半角） → 遍历所有规则：
1. 排除规则优先检查：命中任一个 excludeKeywords → 跳过
2. 检查 requireAll：缺少任一个必含词 → 跳过
3. 检查 keywords：命中数量 → 计算置信度
4. 多个规则同时匹配时：按置信度 × priority 排序，取最高分
5. 最佳匹配与次佳匹配分差 < 0.2 → 认为区分度不够，降级到语义匹配

### 4.2 置信度计算规则

计算公式（仅基于关键词命中情况，不涉及 LLM）：

```
基础分:         0.85
每命中一个关键词: +0.05
独占场景:        +0.05（该场景无其他同时匹配）
每缺失一个关键词: -0.02（从场景总关键词数计算）
────────────────────────────────────────
上限: 1.0，下限: 0.0
```

**设计理由**：
- 以 0.85 为基础分，表示"一个关键词命中就已经足够可信"
- 增加命中数逐步加分，鼓励用户提供更多信息
- 独占场景加分，减少场景间模糊
- 缺失关键词扣分，惩罚信息不足

### 4.3 参数提取规则

从输入中提取结构化的查询参数，支持以下类型：

| 参数类型 | 匹配规则 | 示例 |
|---------|---------|------|
| SKU | 正则 `SKU[-]?\d{3,10}` | "SKU-12345" → skuCode="SKU-12345" |
| 仓库名称 | 名称列表匹配 | "深圳仓" → warehouseName="深圳仓" |
| 时间范围 | 关键词映射 | "今天"→当天、"本周"→周一至今、"本月"→当月1日至今、"近7天"→7天前 |
| 订单编号 | 正则 `(RK\|CK\|PD\|EX\|RT)[-]?\d+` | "CK-0089" → orderNo="CK-0089" |
| 订单 ID | 正则 `ID[为是]?(\d+)` | "ID为123" → orderId=123 |

参数提取不依赖 LLM，全部通过正则和关键词映射完成，保证零成本、零延迟。

## 五、SemanticMatcher — LLM 语义匹配

### 5.1 适用场景

KeywordMatcher 无法处理的三种情况，交给 LLM：

```
1. 口语化/非标准化表达:
   "看看仓库东西够不够" → 关键词匹配无命中 → LLM推断 → stockout_risk (0.82)

2. 同义词/近义词变体:
   "盘点一下深圳仓有多少货" → 关键词命中"盘点"但也命中"仓" → 置信度冲突

3. 需要理解意图而非字面:
   "iPhone 15 还多吗" → 无标准关键词 → LLM推断 → inventory_query + sku参数
```

### 5.2 调用策略

只在 KeywordMatcher 置信度不足时调用。

**工作方式**：
1. 构建 Prompt，注入所有已注册场景的 ID、描述、示例输入
2. 调用 LLM（用 Haiku 级别即可，意图分类是轻量任务）
3. LLM 返回结构化结果（场景ID + 置信度 + 提取的参数）
4. 如果 LLM 返回的置信度 ≥ 0.50 → 确认后执行
5. 如果 0.20~0.50 → 返回候选选项
6. 如果 < 0.20 → 走兜底

**Prompt 模板结构**（设计要点）：

```
1. 系统角色定义：你是一个 WMS 仓库管理系统的意图识别助手
2. 场景清单注入：所有已注册场景的描述 + 示例输入（每个场景 2~3 个示例）
3. 输入格式要求：请返回 JSON 格式
4. 负样本说明：如果不匹配任何场景，返回空
5. 用户输入：{实际用户输入}

输出格式（结构化）：
{
  "sceneId": "WM_COMPLEX_002",
  "confidence": 0.0~1.0,
  "params": { "warehouseId": 1, "timeRange": "MONTH" }
}
```

### 5.3 降级策略

LLM 不可用时的备用方案，基于文本相似度：

1. 将用户输入与每个场景的示例文本做 Jaccard 相似度计算
2. 取最高相似度值
3. 阈值设为 0.25（低于正常语义匹配，考虑到没有 LLM 的理解能力）
4. 如果命中，将置信度乘以 0.7 作为最终置信度（降级惩罚）

此方案只在 LLM 超时或 API 不可用时触发，正常情况下不经过此路径。

## 六、MultiIntentMatcher — 多意图拆解

### 6.1 匹配逻辑

检测用户输入是否包含多个独立意图，规则如下：

**判定条件（同时满足）**：
1. 输入中包含连接词："和"、"与"、"以及"、"还有"、"、"（顿号）
2. 按连接词拆解后，每个部分都能独立匹配到场景（KeywordMatcher 置信度 > 0.6）
3. 不是"先A后B"的顺序关系（如"先入库再出库"不算多意图）

**拆解规则**：
- "查下库存和异常" → ["查下库存", "异常"] → inventory_list + exception_list
- "库存和异常情况" → ["库存", "异常情况"] → inventory_list + exception_list
- "查看库存、出库单和异常" → ["查看库存", "出库单", "异常"] → 三个意图并行

**限制**：最多支持 3 个意图并行拆解，超过 3 个部分时认为输入过于复杂，交给 LLM 处理。

### 6.2 评测用例覆盖

| 评测用例 | 输入 | 拆解结果 |
|---------|------|---------|
| 模糊#6 | "查下库存和异常" | → inventory_list + exception_list |
| 扩展 | "看出库单和退货单" | → outbound_list + return_list |
| 扩展 | "查库存、出库单和异常" | → 三个意图并行 |

## 七、ConversationContext — 多轮对话上下文

### 7.1 指代消解

处理用户输入中隐含的指代关系，解决"那个产品"、"处理一下"等不完整输入。

**触发条件**：

| 模式 | 示例 | 说明 |
|------|------|------|
| 代词 | "那个"、"这个"、"它"、"这些"、"那些" | 指代上文出现的实体 |
| 属性词 | "该产品"、"上述订单"、"刚才的异常" | 引用上文的特定实体 |
| 短命令 | "处理"、"看看"、"查查"、"操作" | 操作对象在上文中 |

**解析策略**：

1. 从历史消息中取最后一条用户消息的识别结果
2. 提取上文中出现的 sceneId 和 params（如 SKU、订单 ID）
3. 根据当前输入的类型决定如何复用上文的参数：

| 场景 | 当前输入 | 上文有 | 解析结果 |
|------|---------|--------|---------|
| 模糊#7 | "那个产品有问题" | SKU-12345 | → 查 SKU-12345 的异常 |
| 模糊#8 | "处理一下" | EX-001 异常单 | → 跳转到异常处理场景 |
| 扩展 | "它库存多少" | SKU-12345 | → 查 SKU-12345 的库存 |

**上下文有效期**：只取最近一轮对话的上文。多轮之前的数据不保留，避免指代错乱。

## 八、Query Preprocessor — 匹配前预处理

### 8.1 为什么需要预处理层

用户的原始输入有三种情况会导致匹配引擎"白费力"：

| 输入类型 | 问题 | 表现 |
|---------|------|------|
| 越界请求 | "帮我预测下个月销售额" | 匹配引擎遍历全部规则最终全不命中，白白浪费时间 |
| 口语化 | "看看仓库东西够不够" | KeywordMatcher 一个词都命不中，必须走 SemanticMatcher 兜底 |
| 歧义输入 | "最近的单子" | 可以理解为入库单/出库单/盘点单/异常单，需要一个确定 |

如果没有预处理层，以上三种情况都要走完完整匹配链才知道结果（越界请求浪费 50ms+，口语化浪费 500ms+ LLM 调用）。**预处理层在匹配前就把问题处理掉，减少无效匹配，提高精确匹配率。**

预处理层位于用户输入和 IntentRecognizer 之间：

```
用户输入 → Query Preprocessor → 改写后的 query(s) → IntentRecognizer → ...
```

### 8.2 Intent Boundary Detection — 意图边界检测

在匹配之前，快速判断用户输入是否越界。越界指三种情况：

| 边界类型 | 检测规则 | 示例 | 处理方式 |
|---------|---------|------|---------|
| 权限越界 | 命中权限黑名单关键词（"采购价"、"成本"、"提成"、"薪资"） | "供应商深圳XX电子的采购价是多少" | → 直接拒绝 |
| 能力越界 | 检测到的动词不在 Agent 能力列表中 | "帮我预测下个月销售额" | → 引导替代方案 |
| 安全越界 | 命中安全黑名单模式（SQL 注入、越权尝试） | "删除所有库存数据" | → 安全拒绝 |

**实现方式**：规则匹配 + 正则，不调 LLM，< 5ms 完成。

```
检测流程:
输入 → 归一化 → 遍历边界规则:
  ├─ 命中安全黑名单    → SecurityGate ("无法处理该请求")
  ├─ 命中权限黑名单    → SecurityGate ("您没有访问xx的权限")
  ├─ 能力范围检查     → Fallback ("我不具备该能力，您可以...")
  └─ 全部通过         → 继续到下一阶段
```

越界检测通过后，输入进入重写阶段。

### 8.3 Query Rewriter — 重写模糊 query

把口语化、指代不清的输入改写成匹配引擎更容易命中的标准化形式。

**核心逻辑**：用 Haiku 级别 LLM 做轻量改写（不是完整匹配，只是重写）。

```
用户输入: "仓库的库存情况怎么样"
当前上下文: 无（进入本节时未检测到多意图）

Prompt 模板:
  请将以下仓库管理相关的用户输入改写为更明确、标准化的查询指令。
  如果输入涉及代词（那个、这个、它），用上下文中的具体实体替换。
  如果输入包含多个需求，拆分为多条指令。

  用户输入: "{原始输入}"

  输出 JSON 格式:
  {"rewrittenQueries": ["改写后的查询1", ...], "reason": "改写原因"}
```

**改写效果**：

| 原始输入 | 改写后 | 效果 |
|---------|--------|------|
| "仓库的库存情况怎么样" | → ["查询库存汇总"] | 口语→标准，KeywordMatcher 直接从 0.25 跳到 0.90 |
| "东西不够了" | → ["查询库存不足的SKU"] | 口语→标准化场景 |
| "看看深圳仓还有多少货" | → ["查询深圳仓库存汇总"] | 口语+参数→标准 |
| "最近有点慢" | → ["分析入库效率", "分析出库效率", "分析库存周转率"] | 单一模糊→三个明确意图 |
| "那个产品有问题" | → ["查询SKU-12345的异常记录"] | 指代消解在改写阶段完成 |

**改写规则**：

| 改写类型 | 说明 | 示例 |
|---------|------|------|
| 口语→标准 | 将口语化表达转为标准化查询 | "看看"→"查询"、"够不够"→"库存是否充足" |
| 指代→实体 | 用具体实体替换代词 | "那个产品"→"SKU-12345" |
| 拆分 | 将多需求拆为多条 query | "有点慢"→入库效率+出库效率+周转率 |
| 补全 | 补充缺失的关键词 | "最近的单子"→"最近的入库单/出库单/..." |

**响应目标**：< 300ms（Haiku 级别模型）。

### 8.4 Query Expander — 扩展歧义 query

当一个输入有多个合理的理解方向时，扩展成多条 query 分别覆盖：

```
原始: "查询库存"
    ├─ 扩展1: "查询库存列表"       → 目标场景 WM_SIMPLE_001
    ├─ 扩展2: "查询库存汇总统计"   → 目标场景 WM_SIMPLE_003
    └─ 扩展3: "查询库存分布情况"   → 目标场景 WM_MEDIUM_001

原始: "最近的单子"
    ├─ 扩展1: "查询最近的入库单"   → WM_SIMPLE_004
    ├─ 扩展2: "查询最近的出库单"   → WM_SIMPLE_005
    ├─ 扩展3: "查询最近的盘点单"   → WM_SIMPLE_007
    └─ 扩展4: "查询最近的异常单"   → WM_SIMPLE_008
```

**扩展现则在 Rewriter 输出的基础上进行**——不重新写一条，而是把已经标准化但仍有歧义的 query 展开：

```
输入: "查询库存" — 已经标准化，但"库存"可以指列表/汇总/分布
  → Expander 判断: 有多义性
  → 扩展为 3 条精确 query

输入: "查询SKU-12345的库存分布" — 已经精确
  → Expander 判断: 无歧义
  → 不扩展，原样输出
```

**扩展后的匹配结果取舍**：

```
N 条扩展 query 分别匹配完成后:

├─ 全部命中同一个 sceneId
│   └─ 合并参数 → 执行一次
│      e.g. "查SKU-12345和SKU-67890" → 都命中 WM_SIMPLE_001
│      → 合并 skuCodes=["SKU-12345", "SKU-67890"]
│
├─ 命中不同 sceneId，最高分 ≥0.85 且领先第二名 ≥0.2
│   └─ 只取最高分那条 → 执行
│      e.g. "查询库存汇总"(0.95) vs "查询库存分布"(0.70)
│      → 取汇总，用户无感知
│
├─ 命中不同 sceneId，分数接近（分差 < 0.2）
│   └─ 展示为排序后的选项 → 用户选哪个就执行哪个
│      e.g. "最近的单子"→ 4 条都 0.85+，分差 < 0.1
│      → 展示选项，比原来的模糊选项更精准
│
└─ 全部命中置信度 < 0.50
    └─ 展示为选项 → 走原 OptionPresenter 流程
```

**关键原则**：**不执行多条**，只取一条执行或展示为选项。Expansion 的作用是让选项更精确，不是并行执行。

### 8.5 三种预处理的关系

```
用户输入
    │
    ▼
┌─────────────────────────────────────────────────┐
│ 1. Intent Boundary Detection (规则匹配, < 5ms)   │
│    越界 → 直接拒绝                               │
│    通过 → 继续                                   │
└──────────────────────┬──────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────┐
│ 2. Query Rewriter (Haiku LLM, < 300ms)          │
│    口语化→标准化                                  │
│    指代消解                                       │
│    输出: 1条或多条标准化 query                     │
└──────────────────────┬──────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────┐
│ 3. Query Expander (规则+LLM, < 200ms)           │
│    歧义→扩展                                      │
│    无歧义→原样输出                                 │
│    输出: 1~4 条精确 query                         │
└──────────────────────┬──────────────────────────┘
                       │
                       ▼
                 改写后的 query(s)
                  → IntentRecognizer

### 9.1 为什么需要路由层

意图识别（IntentRecognizer）只回答"用户想干什么"——它输出一个 sceneId + 置信度 + 参数。但"知道用户想干什么"和"下一步该做什么"是两件事。

同一个 sceneId，在不同条件下可能走不同路径：

| 场景 | 场景ID | 条件 | 应该走哪条路 |
|------|--------|------|-------------|
| 查库存列表 | WM_SIMPLE_001 | 用户有权限 | → 调用工具查询数据 |
| 查库存列表 | WM_SIMPLE_001 | 用户没权限 | → 安全拒绝，不走工具 |
| 库存情况怎么样 | WM_AMBIGUOUS_001 | 置信度<0.50 | → 返回选项让用户选，不查数据 |
| 库存情况怎么样 | WM_AMBIGUOUS_001 | 置信度≥0.85 | → 直接执行 |
| 那个产品有问题 | WM_AMBIGUOUS_007 | 上文有SKU | → 解析后调工具查异常 |
| 那个产品有问题 | WM_AMBIGUOUS_007 | 上文无SKU | → 反问用户具体产品 |
| 东西不够了 | WM_AMBIGUOUS_002 | 简单回复即可 | → RAG查库存预警规则再回答 |
| 东西不够了 | WM_AMBIGUOUS_002 | 需要深入分析 | → 调LLM做缺货推理 |

所以意图识别之后需要一个 **IntentRouter**，它根据 IntentResult 的内容（sceneId、confidence、params、用户角色）决定下一步把请求路由到哪里。

### 9.2 路由目标

| 路由目标 | 说明 | 触发条件 |
|---------|------|---------|
| **LLM Planner** (计划生成) | 负责边界检查 + 生成执行计划，**这是主路径** | confidence≥0.85，或确认后≥0.85 |
| **用户确认** (ConfirmationGate) | 向用户展示确认信息，等用户点头再执行 | 0.50≤confidence<0.85 |
| **选项引导** (OptionPresenter) | 向用户展示多个候选场景，让用户选 | 0.20≤confidence<0.50 |
| **信息索取** (InfoCollector) | 反问用户，补充缺失的参数 | 置信度够但缺关键参数（如没说明哪个仓库） |
| **安全拦截** (SecurityGate) | 直接拒绝，不执行任何操作 | 违反权限/安全规则（由LLM Planner或预检触发） |
| **兜底回答** (Fallback) | 无法理解用户意图时的通用回复 | confidence<0.20，且指代消解失败 |

> **注意**: 8.2 节列出的路由目标是 IntentRouter 直接分发的第一跳目标。
> LLM Planner 收到请求后内部还会做安全边界检查、生成执行计划，
> 然后将计划交给 Determinate Executor 执行，最后由 LLM Analyst 分析结果。
> 这些是 LLM Planner 内部的子流程，不是 IntentRouter 直接分发的目标。

### 9.3 路由决策表

路由不是简单的 if-else，而是根据 **IntentResult** 的多个字段联合决策：

```
IntentResult 进入 Router:
│
├─ 置信度 + 场景配置 → 决定路由目标:
│  │
│  ├─ confidence≥0.85 ──→ 检查参数完整性
│  │  ├─ 参数完整       → LLM Planner（出执行计划 + 边界检查）
│  │  ├─ 缺关键参数     → InfoCollector（反问用户补充参数）
│  │  └─ 场景标记了NEEDS_CLARIFY → OptionPresenter（先让用户选）
│  │
│  ├─ 0.50≤confidence<0.85 ──→ ConfirmationGate
│  │  ├─ 用户确认       → LLM Planner
│  │  └─ 用户否定       → OptionPresenter 或 InfoCollector
│  │
│  ├─ 0.20≤confidence<0.50 ──→ OptionPresenter
│  │  ├─ 用户选了某个选项 → 按选中的 sceneId 重新路由
│  │  └─ 用户继续模糊   → InfoCollector（引导用户提供更多信息）
│  │
│  └─ confidence<0.20 ──→ 指代消解
│     ├─ 解析成功       → LLM Planner
│     └─ 解析失败       → Fallback（"抱歉，我没有理解您的意思"）
│
└─ 场景类型后路由 ────────────────────── 场景特定的额外判断
   ├─ sceneType=RAG_QUERY        → RAGKnowledge（不走工具链）
   ├─ sceneType=SECURITY_CHECK   → SecurityGate（走安全拦截）
   └─ sceneType=NEEDS_CLARIFY   → InfoCollector（先收集信息）
```

### 9.4 各路由Handler的职责说明

**LLM Planner** — 出执行计划 + 边界判断（主路径的第一站）：
- 接收 sceneId + params + 用户角色
- **先做边界安全检查**（见第 X 节：LLM Planner 的边界处理）
- 边界通过后，根据场景生成执行计划（工具步骤 + 条件分支 + 参数映射）
- 输出 ExecutionPlan，交给 Determinate Executor
- 这是整个路由的核心，大部分请求最终都经过这里

**ConfirmationGate** — 用户确认门：
- 向用户展示："您是想查询[场景描述]吗？参数是[xxx]，对吗？"
- 用户确认 → 透传给 LLM Planner
- 用户否定 → 退回 OptionPresenter 或 InfoCollector
- 用户补充参数 → 更新 params 后透传

**OptionPresenter** — 候选选项展示：
- 收到 IntentResult.candidateScenes 列表
- 组装成友好的选项消息（带 emoji、说明、快捷指令）
- 用户选择后，带着选中的 sceneId 重新进入 Router

**InfoCollector** — 信息收集（反问用户）：
- 检测到缺失的关键参数时触发
- 根据场景配置的 requiredParams 逐一询问
- 示例：场景需要 warehouseId 但用户没提 → "请问您想查哪个仓库？（深圳仓/上海仓/越南仓/泰国仓）"
- 收集完所有必要参数后，透传给 LLM Planner

**RAGKnowledge** — 知识库查询：
- 不走工具链，直接从知识库（YAML规则/文档）检索答案
- 适用于"缺货分级标准是什么"、"补货策略怎么配"这类元问题
- 检索结果直接组装回答，不调用数据工具

**SecurityGate** — 安全拦截：
- 权限校验：用户角色是否允许执行该场景
- 敏感操作拦截：涉及成本数据、供应商价格等敏感信息
- 输入安全检测：命中黑名单关键词（如尝试越权的输入）
- 拦截后返回友好但明确的拒绝信息

**Fallback** — 兜底回复：
- 适用于完全无法理解用户意图的情况
- 可以提供通用指引："我是仓库管理助手，您可以问我库存查询、出库单、盘点等问题"
- 或者引导用户到帮助中心

### 9.5 路由配置

路由配置是每个场景定义的一部分，指明意图识别后应如何路由到 LLM Planner：

| 配置项 | 说明 | 可选值 |
|--------|------|--------|
| routeType | 主路由类型 | DATA_QUERY / RAG_QUERY / NEEDS_CLARIFY / SECURITY_CHECK |
| requiredParams | 执行所需的参数列表 | ["warehouseId", "skuCode", "timeRange"] |
| needsLLM | 执行后是否需要LLM分析数据 | true / false |
| securityCheck | 是否需要LLM Planner做安全检查 | true / false |
| timeout | 执行超时（毫秒） | 1000~10000 |

**示例**：

```
WM_SIMPLE_001（查询库存列表）
  routeType: DATA_QUERY          # 走LLM Planner → 生成线性计划 → Determinate Executor
  requiredParams: []              # 不需要参数
  needsLLM: false                 # 纯数据查询，不需要LLM分析
  securityCheck: false            # 库存列表不需要额外安全检查
  timeout: 2000

WM_COMPLEX_001（运营效率诊断）
  routeType: DATA_QUERY          # 走LLM Planner → 生成条件分支计划 → Executor → LLM Analyst
  requiredParams: [warehouseId, timeRange]
  needsLLM: true                  # 数据查完后需要LLM做深度分析
  securityCheck: true
  timeout: 8000

WM_AMBIGUOUS_001（库存情况怎么样）
  routeType: NEEDS_CLARIFY       # 走选项引导，不进LLM Planner
  requiredParams: []
  confidenceAction: OPTIONS       # 低置信度时走选项引导

WM_SIMPLE_006（出库单详情）
  routeType: DATA_QUERY
  requiredParams: [orderId]       # 缺orderId时需要InfoCollector反问
  securityCheck: true             # 出库单详情可能含敏感信息
  timeout: 2000
```

### 9.6 路由层的价值总结

加入 IntentRouter 后，系统的完整链路变为：

```
用户输入 → IntentRecognizer → IntentResult → IntentRouter → LLM Planner
  → Determinate Executor → LLM Analyst → OutputFormatter
```

| 没有路由层 | 有路由层 |
|-----------|---------|
| 识别后只能"执行或兜底" | 6种路由目标，灵活分流 |
| 安全校验散落在各个场景里 | 统一在路由层和LLM Planner做安全检查 |
| 参数缺失时直接报错 | InfoCollector 优雅反问用户 |
| 模糊场景只能硬兜底 | OptionPresenter 给选项让用户选 |
| 场景类型混在一起判断 | 按 sceneType 分流到不同处理器 |

路由层的核心价值是**把"识别"和"执行"解耦**——意图识别只管猜用户想干什么，路由层才决定怎么干。这样两个模块可以独立演进：识别算法换了好几次，路由逻辑不用动；新增路由目标（比如将来加一个"转人工"），也不用改识别流程。

## 十、LLM Planner — 计划生成 + 边界判断

### 10.1 角色定位

LLM Planner 是整个 Agent 系统中**唯一负责推理决策**的 LLM 组件。它的职责是接收"用户想干什么"（sceneId + params），决定"能不能做、怎么做"。

它与 SemanticMatcher 和 LLM Analyst 的区别：

| LLM 角色 | 位置 | 做什么 | 模型要求 |
|---------|------|--------|---------|
| SemanticMatcher | 意图识别阶段 | 理解模糊输入 → 输出 sceneId | Haiku |
| **LLM Planner** | 路由后、执行前 | 边界检查 → 生成执行计划 | Sonnet |
| LLM Analyst | 执行后 | 读数据 → 分析报告 | Sonnet |

### 10.2 边界安全检查（能不能做）

LLM Planner 在生成执行计划之前，先做一轮边界判断。这是三个问题的统一入口：

```
LLM Planner 收到请求:
  sceneId: WM_COMPLEX_002
  params: { warehouseId: 1 }
  user: { role: WAREHOUSE_MANAGER, userId: 123 }

  第一步：边界检查 Prompt
  ┌─────────────────────────────────────────────────────┐
  │ 用户角色: WAREHOUSE_MANAGER                          │
  │ 请求场景: WM_COMPLEX_002 - 缺货风险评估               │
  │ 请求参数: { warehouseId: 1 (深圳仓) }                 │
  │                                                     │
  │ 请检查以下边界条件:                                   │
  │                                                     │
  │ 1. 权限边界:                                         │
  │    - WAREHOUSE_MANAGER 是否有权访问仓库运营数据?       │
  │      → 是，仓库管理员有权                            │
  │                                                     │
  │ 2. 数据敏感边界:                                     │
  │    - 是否涉及采购价格、供应商合同等敏感数据?            │
  │      → 否，缺货风险只涉及库存数量和出库数据            │
  │                                                     │
  │ 3. 能力边界:                                         │
  │    - 当前可用工具是否能满足该场景的数据需求?            │
  │      → 可用工具清单: [InventoryList, OutboundOrder,  │
  │         SupplierProduct, WarehouseSummary, ...]       │
  │      → 是，有足够工具                                 │
  │                                                     │
  │ 检查结果: PASS                                       │
  └─────────────────────────────────────────────────────┘
```

**三种越界情况**：

| 边界类型 | 发现的问题 | LLM Planner 返回 |
|---------|-----------|-----------------|
| 权限越界 | 仓库管理员查采购价格 | 直接拒绝：不生成计划 |
| 数据敏感 | 查操作员提成数据 | 拒绝或标记 sanitize |
| 能力越界 | "预测下个月销售额"（无此工具） | 拒绝 + 引导替代方案 |

> 边界检查是 LLM Planner 内部的第一步骤，不改变 IntentRouter 的路由逻辑。
> Router 只需要知道"请求来了 → 交给 Planner"，Planner 自己决定能不能做。

### 10.3 生成执行计划（怎么做）

边界检查通过后，LLM Planner 生成动态执行计划。计划包含：

| 计划要素 | 说明 | 示例 |
|---------|------|------|
| steps | 步骤列表（有序） | InventoryListTool → OutboundOrderTool |
| params | 每步的参数映射 | { "skuCode": "SKU-12345" } |
| dependencies | 步骤间的数据依赖 | 第二步依赖第一步输出的 productId |
| conditions | 条件分支 | 如果库存 < 安全线 → 调 SupplierTool |
| parallel | 并行组 | { ExpiryWarningTool, LocationTool } 可同时调 |

**简单场景（线性计划）**：

```
输入: "查询库存列表"  (WM_SIMPLE_001)

计划:
  steps:
    - tool: InventoryListTool
      params: { page: 1, limit: 20 }
      description: "查询库存列表"
```

**中等场景（串行依赖计划）**：

```
输入: "查询SKU-12345在各个仓库的库存分布"  (WM_MEDIUM_001)

计划:
  steps:
    - tool: ProductQueryTool
      params: { skuCode: "SKU-12345" }
      outputKey: productInfo           # 结果存为 productInfo

    - tool: InventoryDetailTool
      params: { productId: "${productInfo.id}" }    # 引用上一步结果
      description: "查各仓库库存分布"

  parallel:                             # 并行组
    - tool: ExpiryWarningTool
      params: { skuCode: "SKU-12345" }
```

**复杂场景（条件分支计划）**：

```
输入: "分析未来7天可能缺货的SKU"  (WM_COMPLEX_002)

计划:
  steps:
    - tool: InventoryListTool
      params: { pageSize: 200 }
      description: "查所有SKU库存"

    - tool: OutboundOrderTool
      params: { days: 7, status: "COMPLETED" }
      dependsOn: [InventoryListTool]    # 用库存数据的SKU列表
      description: "计算日均消耗量"

    # 条件分支: 只有缺货风险高的SKU才查供应商
    - tool: SupplierProductTool
      params: { productIds: "${steps[1].highRiskSkus}" }
      condition: "${steps[1].hasHighRisk == true}"
      description: "查高风险SKU的供应商补货周期"
      optional: false

  parallel:
    - tool: WarehouseSummaryTool
      description: "查其他仓库库存（跨仓调拨参考）"
      optional: true                    # 非必需，失败不影响主流程

  postProcess:
    - name: "computeRiskLevel"
      formula: "currentStock / dailyConsumption → 风险等级"
```

### 10.4 与 Determinate Executor 的分工

```
LLM Planner           Determinate Executor         LLM Analyst
(出计划)                 (跑计划)                    (分析数据)
    │                       │                           │
    │  ExecutionPlan         │                           │
    ├─────────────────────►  │                           │
    │                       │  step1: InventoryList      │
    │                       │  ├── 调 Controller         │
    │                       │  └── 存结果                 │
    │                       │                           │
    │                       │  step2: 检查条件            │
    │                       │  ├── hasHighRisk? → true  │
    │                       │  └── 继续执行 SupplierTool │
    │                       │                           │
    │                       │  step3: SupplierProduct    │
    │                       │  ├── 调 Controller         │
    │                       │  └── 存结果                 │
    │                       │                           │
    │                       │  ScenarioResult            │
    │                       ├──────────────────────────► │
    │                       │                           │  深度分析报告
    │                       │                           ├────────────►
```

| 组件 | 是否调LLM | 负责 |
|------|----------|------|
| LLM Planner | 是（每次请求） | 边界检查 + 生成 ExecutionPlan |
| Determinate Executor | **否** | 遍历步骤、调工具、传参数、判条件 |
| LLM Analyst | 是（仅 needsLLM=true） | 读数据写分析报告 |

**执行器不调 LLM**——它只做四件事：
1. 遍历 ExecutionPlan 的 steps
2. 如果有 condition，计算条件（true/false，不推理）
3. 如果有依赖，从之前的结果映射参数
4. 调用工具，收集结果

这样保证了执行过程的确定性和可重复性。

### 10.5 边界情况汇总

| 边界类型 | 触发条件 | LLM Planner 的处理 |
|---------|---------|-------------------|
| 权限越界 | 用户角色无权执行该场景 | 返回拒绝消息，不生成计划 |
| 数据敏感 | 请求涉及敏感字段 | 返回拒绝消息，或标记 sanitize=true |
| 能力越界 | 请求超出工具范围 | 返回引导消息，建议替代方案 |
| 参数不足 | 缺少必要参数 | 反问用户补充（走 InfoCollector） |
| 依赖缺失 | 上游工具返回值异常 | 标记为 optional=true 跳过，或终止计划 |
| 条件不满足 | condition=false | 跳过该步骤，继续执行后续

## 十一、置信度决策流程

```
用户输入
    │
    ▼
Query Preprocessor ──── 越界 ──→ SecurityGate（拒绝）
    │
    通过
    │
    ▼
KeywordMatcher ──── ≥0.85 ──→ 执行 (简单全量、中等大部分)
    │
    0.50~0.85 ──→ 执行+确认 ("您是想查深圳仓吗？")
    │
    0.20~0.50 ──→ SemanticMatcher(LLM) ──→ ≥0.50 ──→ 确认后执行
    │                                            │
    │                                            0.20~0.50 ──→ 返回选项
    │
    <0.20 ──→ ConversationContext(指代消解) ──→ 命中 ──→ 执行
                         │
                         未命中 ──→ 兜底回答
```

### 各区间行为定义

| 置信度区间 | 行为 | 适用场景 |
|-----------|------|---------|
| ≥ 0.85 | 直接执行，不询问用户 | 简单 10 题、中等大部分 |
| 0.50 ~ 0.85 | 执行后向用户确认 | KeywordMatcher 命中但参数不足、SemanticMatcher 结果 |
| 0.20 ~ 0.50 | 返回候选选项供用户选择 | 模糊 #1~#5 |
| < 0.20 | 先指代消解，再兜底 | 模糊 #7~#8、完全无匹配 |

### 阈值配置项

四个关键阈值应当外部化配置，支持按环境调整：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| confidence.high | 0.85 | 直接执行阈值 |
| confidence.medium | 0.50 | 确认后执行阈值 |
| confidence.low | 0.20 | 返回选项阈值 |
| confidence.fallback | 0.10 | 兜底阈值 |

## 十二、评测验证方式

### 12.1 分层验证

**单元验证（每类场景抽样 1~2 题）**：

| 测试维度 | 输入示例 | 验证点 |
|---------|---------|--------|
| 越界检测 | "查询供应商采购价格" | → 不走匹配链，直接返回拒绝 |
| Query Rewriter | "仓库的库存情况怎么样" | → 改写为"查询库存汇总"，后续匹配 WM_SIMPLE_003 ≥0.85 |
| Query Expander | "最近的单子" | → 扩展为 4 条精确 query，展示为选项 |
| 简单题精确匹配 | "查询库存列表" | sceneId=WM_SIMPLE_001, confidence≥0.85 |
| 中等题参数提取 | "查询SKU-12345在各个仓库的库存分布" | sceneId=WM_MEDIUM_001, params.skuCode="SKU-12345" |
| 模糊题候选返回 | "仓库的库存情况怎么样" | confidence<0.50, candidates 非空 |
| 多意图拆解 | "查下库存和异常" | 返回 2 个 IntentResult |
| 指代消解 | "那个产品有问题" + 上文有 SKU-12345 | params.skuCode="SKU-12345" |

**批量评估（全部 36 题）**：

所有 36 题按照评测规范逐条验证，统计最终准确率：

| 难度 | 题数 | 期望置信度 | 验证方式 |
|------|------|-----------|---------|
| 简单 | 10 题 | ≥ 0.85 | ExactMatch: sceneId + confidence |
| 中等 | 10 题 | ≥ 0.85 | ExactMatch: sceneId + params |
| 复杂 | 3 题 | ≥ 0.70 | SemanticMatch: sceneId |
| 模糊 | 8 题 | < 0.50 | CandidateCheck: candidates 非空 |

### 12.2 通过标准

| 指标 | 目标 |
|------|------|
| 整体准确率 | ≥ 90% |
| 简单 10 题准确率 | 100%（必须全部正确） |
| 中等 10 题准确率 | ≥ 90% |
| 复杂 3 题准确率 | ≥ 75% |
| 模糊 8 题准确率 | ≥ 65%（仅要求正确识别模糊类型，给出合理候选） |

## 十三、与开发计划的关系

```
第一期（当前优先）：
  意图识别 → 硬编码评测集关键词 + 参数提取 + 基础预处理
  → KeyWordMatcher 覆盖 简单10题 + 中等10题（80%准确率来源）
  → Query Preprocessor 基础版（边界检测 + 简单规则重写）

第二期（LLM集成后）：
  + Query Rewriter (Haiku) 覆盖 口语化/模糊输入
  + Query Expander (规则+LLM) 覆盖 歧义输入
  + SemanticMatcher 覆盖 复杂3题 + 模糊5题
  + MultiIntentMatcher 覆盖 模糊#6

第三期（YAML通用化后）：
  场景配置外移至YAML，意图识别规则也外移
  预处理规则（重写/扩展/边界）也外移至YAML配置
```

### 注意事项

- **KeywordMatcher 是准确率基石**：简单+中等 20 题占评测集的 55%，全部由关键词匹配零成本覆盖，不依赖外部服务
- **SemanticMatcher 是兜底网**：只处理 KeywordMatcher 吞不掉的复杂/模糊情况，使用 Haiku 级别模型即可
- **配置与引擎分离**：第一期关键词规则硬编码，第三期外移到 YAML，核心匹配流程不受影响
- **ConversationContext 是锦上添花**：只解决模糊 #7~#8，不参与主要流程
