## 一、评分维度

### 1.1 五大核心维度

| 维度 | 权重 | 说明 | 评分要点 |
|------|------|------|----------|
| **准确性** | 40% | 数据是否正确、完整 | 数值准确、逻辑正确、无遗漏 |
| **完整性** | 20% | 是否包含所有必要信息 | 信息全面、字段完整、上下文清晰 |
| **可用性** | 20% | 用户能否直接使用答案 | 方案可行、步骤清晰、可直接操作 |
| **友好性** | 10% | 格式是否清晰易读 | 排版美观、表达简洁、重点突出 |
| **时效性** | 10% | 响应速度是否达标 | 符合时间要求、无明显延迟 |

### 1.2 维度详细说明

#### 准确性（Accuracy）- 40分

**评分标准**:

| 分值 | 标准 | 说明 |
|------|------|------|
| 40分 | 完全准确 | 所有数据正确无误，逻辑严密 |
| 30分 | 基本准确 | 核心数据正确，次要信息有少量偏差（<5%） |
| 20分 | 部分准确 | 关键数据有误，但不影响主要结论（偏差5-20%） |
| 10分 | 严重错误 | 核心数据错误，结论不可信（偏差>20%） |
| 0分 | 完全错误 | 数据完全错误或无响应 |

**示例**:

```
用户输入: "SKU-12345的库存是多少？"

✅ 40分 - 完全准确
"SKU-12345 当前库存为 1,234 件，其中可用库存 1,200 件，锁定库存 34 件。"

⚠️ 20分 - 部分准确
"SKU-12345 当前库存为 1,200 件。"（缺少可用/锁定分类）

❌ 0分 - 完全错误
"SKU-12345 当前库存为 500 件。"（数据错误）
```

---

#### 完整性（Completeness）- 20分

**评分标准**:

| 分值 | 标准 | 说明 |
|------|------|------|
| 20分 | 完整全面 | 包含所有必要信息，无遗漏 |
| 15分 | 基本完整 | 包含主要信息，次要信息略有缺失 |
| 10分 | 部分完整 | 缺少关键信息，需用户追问 |
| 5分 | 严重缺失 | 信息不完整，无法满足需求 |
| 0分 | 无响应 | 未提供任何有效信息 |

**示例**:

```
用户输入: "我的待办任务有哪些？"

✅ 20分 - 完整全面
"📋 您当前有 5 项待办任务：
1. 入库单 RK-001 待质检（优先级：高）
2. 出库单 CK-089 拣货异常待处理（优先级：高）
3. 盘点单 PD-003 盘点差异需确认（优先级：中）
4. 库存预警 SKU-12345 库存不足（优先级：中）
5. 效期预警 SKU-67890 将于3天后过期（优先级：低）

💡 建议：优先处理出库单异常，避免影响发货时效。"

⚠️ 10分 - 部分完整
"您有 5 项待办任务。"（缺少任务详情）

❌ 5分 - 严重缺失
"有任务待处理。"（信息不足）
```

---

#### 可用性（Usability）- 20分

**评分标准**:

| 分值 | 标准 | 说明 |
|------|------|------|
| 20分 | 可直接使用 | 答案清晰明确，用户可直接操作 |
| 15分 | 基本可用 | 需少量思考或补充操作 |
| 10分 | 需进一步确认 | 答案模糊，需用户验证或追问 |
| 5分 | 难以使用 | 答案不明确，需大量额外工作 |
| 0分 | 不可用 | 无法理解或误导用户 |

**示例**:

```
用户输入: "哪些产品库存低于安全库存？"

✅ 20分 - 可直接使用
"以下 3 个产品库存低于安全库存：

| SKU | 产品名称 | 当前库存 | 安全库存 | 差异 | 建议 |
|-----|---------|---------|---------|------|------|
| SKU-12345 | 产品A | 50 | 100 | -50 | 建议补货 100 件 |
| SKU-23456 | 产品B | 80 | 120 | -40 | 建议补货 80 件 |
| SKU-34567 | 产品C | 30 | 50 | -20 | 建议补货 40 件 |

💡 您可以点击 [补货申请] 快速发起补货流程。"

⚠️ 10分 - 需进一步确认
"有 3 个产品库存低于安全库存：SKU-12345、SKU-23456、SKU-34567。"（缺少具体数据和建议）

❌ 0分 - 不可用
"库存不够。"（无法操作）
```

---

#### 友好性（Friendliness）- 10分

**评分标准**:

| 分值 | 标准 | 说明 |
|------|------|------|
| 10分 | 非常友好 | 格式美观、排版清晰、重点突出 |
| 8分 | 友好 | 格式良好、易读性强 |
| 6分 | 基本友好 | 格式一般，但可读 |
| 3分 | 不够友好 | 格式混乱，阅读困难 |
| 0分 | 难以理解 | 格式极差，无法理解 |

**格式要求**:

✅ **推荐格式**:
- 使用表情符号增强可读性 📊 📋 ⚠️ 💡
- 使用表格展示结构化数据
- 使用列表展示多个项目
- 使用加粗强调关键信息
- 合理分段，避免大段文字

❌ **不推荐格式**:
- 纯文本堆砌
- 缺乏结构化
- 关键信息不突出
- 过度使用格式（加粗、颜色过多）

---

#### 时效性（Timeliness）- 10分

**评分标准**:

| 难度级别 | 目标响应时间 | 10分 | 8分 | 6分 | 3分 | 0分 |
|---------|-------------|------|-----|-----|-----|-----|
| 简单 | < 2秒 | < 2秒 | 2-3秒 | 3-5秒 | 5-10秒 | > 10秒 |
| 中等 | < 5秒 | < 5秒 | 5-7秒 | 7-10秒 | 10-15秒 | > 15秒 |
| 复杂 | < 10秒 | < 10秒 | 10-15秒 | 15-20秒 | 20-30秒 | > 30秒 |
| 模糊 | < 15秒 | < 15秒 | 15-20秒 | 20-30秒 | 30-45秒 | > 45秒 |

**说明**:
- 响应时间从用户提交请求到Agent返回完整响应计算
- 流式响应按第一字节返回时间计算
- 多轮对话按总交互时间计算

## 二、评分标准

### 2.1 总分计算

```
总分 = 准确性(40分) + 完整性(20分) + 可用性(20分) + 友好性(10分) + 时效性(10分)
```

**总分范围**: 0 - 100分

### 2.2 分级标准

| 总分 | 等级 | 评价 | 处理建议 |
|------|------|------|----------|
| 90-100分 | ⭐⭐⭐⭐⭐ 优秀 | 可直接投入使用 | 保持现状 |
| 75-89分 | ⭐⭐⭐⭐ 良好 | 需少量优化 | 针对性改进 |
| 60-74分 | ⭐⭐⭐ 合格 | 需重点改进 | 制定优化计划 |
| 40-59分 | ⭐⭐ 不合格 | 存在严重问题 | 重新设计 |
| 0-39分 | ⭐ 不可用 | 无法使用 | 完全重构 |

## 三、分级评分规则

### 3.1 简单级别评测规则

**特点**: 单一意图、直接查询、快速响应

**重点维度**: 准确性(50%)、时效性(30%)、友好性(20%)

**评分要点**:

| 维度 | 权重 | 重点检查项 |
|------|------|-----------|
| 准确性 | 50% | ✅ 数据100%正确<br>✅ 无歧义<br>✅ 来源可追溯 |
| 时效性 | 30% | ✅ 响应时间 < 2秒<br>✅ 无明显延迟感 |
| 友好性 | 20% | ✅ 格式清晰<br>✅ 易于理解 |
| 完整性 | 0% | - |
| 可用性 | 0% | - |

**示例评分**:

```markdown
用例: "SKU-12345的库存是多少？"

响应: "SKU-12345 当前库存 1,234 件。"

评分:
- 准确性: 50分（数据正确）

- 友好性: 18分（格式清晰）
- 总分: 98分 ⭐⭐⭐⭐⭐
```

| 可用性 | 20% | ✅ 结论明确<br>✅ 可直接使用 |
| 时效性 | 10% | ✅ 响应时间 < 5秒 |
| 友好性 | 5% | ✅ 格式友好 |

**示例评分**:

```markdown
用例: "今天入库完成率是多少？"

响应: "📊 今日入库统计：

- 计划入库单: 20 单

完成率: 75%

💡 剩余 5 单需在今日 18:00 前完成，建议加快验收进度。"

评分:
- 准确性: 40分（计算正确）

- 总分: 98分 ⭐⭐⭐⭐⭐
```

### 3.3 复杂级别评测规则

**特点**: 多数据源、推理建议、跨模块整合

**重点维度**: 可用性(30%)、准确性(30%)、完整性(20%)、时效性(10%)、友好性(10%)

**评分要点**:

| 维度 | 权重 | 重点检查项 |
|------|------|-----------|
| 可用性 | 30% | ✅ 建议合理可行<br>✅ 方案可操作<br>✅ 有明确步骤 |
| 准确性 | 30% | ✅ 数据分析正确<br>✅ 推理逻辑清晰 |
| 完整性 | 20% | ✅ 覆盖多个维度<br>✅ 信息完整全面 |
| 时效性 | 10% | ✅ 响应时间 < 10秒 |
| 友好性 | 10% | ✅ 结构化展示 |

**示例评分**:

```markdown
用例: "分析近期出库效率下降的原因"

响应: "📈 出库效率分析报告（近30天）

### 核心发现
1. **拣货效率下降 15%**
   - 平均拣货时间从 8分钟/单 增至 9.2分钟/单
   - 原因: 新员工占比从 20% 升至 35%

2. **打包环节延迟**
   - 打包等待时间增加 20%
   - 原因: 打包材料库存不足，频繁补货

3. **波次规划不合理**
   - 单波次订单量过大，导致拥堵

### 改进建议
1. ✅ 加强新员工培训（预计提升 8% 效率）
2. ✅ 增加打包材料安全库存（预计减少 15% 等待时间）
3. ✅ 优化波次策略，单波次控制在 50 单以内

### 预期效果
实施上述措施后，预计整体效率可提升 18-22%。"

评分:
- 可用性: 28分（建议可行）
- 准确性: 28分（分析正确）
- 完整性: 20分（信息全面）
- 时效性: 8分（响应9秒）
- 友好性: 9分（结构清晰）
- 总分: 93分 ⭐⭐⭐⭐⭐
```

## 四、评测执行流程

### 4.1 准备阶段

#### 步骤1: 环境准备

```bash
# 检查清单
- [ ] Agent服务已启动
- [ ] 数据库Mock数据已准备
- [ ] 测试账号已创建（每个角色至少1个）
- [ ] 网络连接正常
- [ ] 日志记录工具就绪
```

#### 步骤2: 数据验证

```sql
-- 验证Mock数据完整性
SELECT COUNT(*) FROM sys_user WHERE role = 'WAREHOUSE_MANAGER';
SELECT COUNT(*) FROM inbound_order WHERE status IN (0, 1, 2);
SELECT COUNT(*) FROM inventory WHERE qty > 0;
```

#### 步骤3: 工具准备

- [ ] 评测记录表（Excel/Google Sheets）
- [ ] 计时器（秒表或脚本）
- [ ] 截图工具（记录响应）
- [ ] 日志记录脚本（可选）

---

### 4.2 执行阶段

#### 步骤1: 登录测试账号

```
1. 使用对应角色的测试账号登录
2. 确认角色权限正确
3. 记录测试开始时间
```

#### 步骤2: 执行测试用例

```
1. 按顺序读取测试用例
2. 在Agent对话框输入测试文本
3. 启动计时器
4. 等待Agent响应
5. 停止计时器，记录响应时间
6. 截图保存响应内容
7. 对比期望输出
```

#### 步骤3: 评分记录

```
1. 按五大维度逐项评分
2. 记录差异点
3. 标注问题类型
4. 填写评测记录表
```

#### 步骤4: 异常处理

```
如果出现以下情况，需特殊记录：
- Agent无响应（超时 > 60秒）
- 系统报错（500/503错误）
- 数据明显错误（如负数库存）
- 权限错误（无权访问）
```

### 6.1 发布标准

| 复杂级准确率 | ≥ 70% | ≥ 75% | ≥ 85% |

### 6.2 判定规则

#### 可发布（Green）

```
✅ 整体准确率 ≥ 80%
✅ 所有难度级别准确率达标
✅ 无CRITICAL级别问题
✅ HIGH级别问题 < 3个
```

#### 可发布（Yellow - 需优化）

```
⚠️ 整体准确率 70-80%
⚠️ 个别难度级别略低于目标（差距 < 5%）
⚠️ HIGH级别问题 3-5个
⚠️ 有明确的优化计划
```

#### 不可发布（Red）

```
❌ 整体准确率 < 70%
❌ 简单级准确率 < 90%
❌ 存在CRITICAL级别问题
❌ HIGH级别问题 > 5个
```

### 6.3 问题级别定义

| 级别 | 定义 | 示例 | 处理优先级 |
|------|------|------|-----------|
| **CRITICAL** | 严重功能缺陷，导致系统不可用 | 无响应、系统崩溃、数据泄露 | P0 立即修复 |
| **HIGH** | 主要功能异常，影响用户体验 | 数据错误、逻辑混乱、响应超时 | P1 优先修复 |
| **MEDIUM** | 次要功能问题，影响用户满意度 | 信息缺失、格式不佳 | P2 计划修复 |
| **LOW** | 轻微问题，不影响使用 | 表述优化、格式微调 | P3 可选修复 |

### B. 常见问题FAQ

**Q1: 如果Agent多次返回不同结果，如何评分？**

A: 取最差的一次评分。Agent应保证响应的稳定性。

**Q2: 如果测试数据本身有问题，如何处理？**

A: 标记为"数据异常"，不计入统计，需修复后重新评测。

**Q3: 响应时间包括网络延迟吗？**

A: 是的，响应时间指端到端时间，包含网络传输。建议在稳定网络环境下评测。

**Q4: 模糊级别如何判断意图识别是否正确？**

A: 模糊级别的重点在于引导和澄清，只要Agent提供了有效的选项或引导，即算正确。

**Q5: 多轮对话如何评分？**

A: 按最终结果评分，但响应时间是各轮对话时间之和。
